# Can a recorder's gateway session close and open again while the bot runs?

Research for [Can a recorder's gateway session close and open again while the bot runs? (#845)](https://github.com/7Cav/cavbot2/issues/845), written 2026-10-23. It feeds [How does the recorder's gateway session reconnect? (#843)](https://github.com/7Cav/cavbot2/issues/843), which decided what happens after a cut-short recording. The bot closes that recorder's gateway session with 1000 and opens a new one for the same token, without waiting on the old voice connection. The new open retries on discordgo's schedule, 1 s doubling to 600 s, and stops only when Discord refuses the token. Sentry hears once of an open that keeps failing, after a minute.

The question is whether the bot can do that while it runs, and what on `develop` assumes a recorder opens only at startup.

## Answer

1. **The libraries allow it.** `discordgo.New` builds a session that opens whenever the bot asks, and a disgo voice manager is a plain value tied to one send function. `voice.OpenGateway` already builds the whole stack afresh on every call: the discordgo session, its outage watch, the voice dialer, the disgo voice manager and the two voice event handlers. A second call with the same token gives a second recorder session with the same user ID, and the two share nothing.
2. **`develop` opens each recorder once, at startup, and much of it depends on that.** The recorder list is filled once and can't swap a session or keep a recorder whose open failed. The recording runtime and temp VC copy the recorder user IDs once. A start reserves a recorder without asking whether its session is up, so it can pick one whose session is closed or reopening, and the member gets the ❌ "Something went wrong with the recorder" reply. A stop frees its recorder before a close and reopen could finish. Each failed open goes to Sentry at once and starts no outage. The session's `Close` waits on every voice connection and leaves discordgo's reconnect on. The smoke tally reads recorder lines only until "Bot is now running", and every `OpenGateway` call starts a smoke drop watcher that never stops.
3. **The old voice connection runs on until its leave finishes.** Its voice gateway, UDP keepalive, dialing and any rejoin keep going until then, or until the voice server closes it with 4014. disgo never learns that the gateway session went away. The old discordgo session's handlers stay registered. They get no new events unless that session logs in again by itself, and on discordgo v0.29.0 it can. A `Close` during its reconnect loop doesn't stop the loop, and a heartbeat that fails as the close runs starts one.
4. **discordgo has no retry for a first open.** Its 1 s to 600 s schedule lives in an unexported loop that only a session that was open enters. `Open` makes one try. So "retries on discordgo's own schedule" means the bot runs that loop itself, at those delays. discordgo stops on no close code. On `develop` only the watch stops anything, on 4004.

The last section lists where the code and the libraries meet #843's wording.

## How to read a verdict

- **Works as is.** A fresh session from a second `OpenGateway` call needs nothing from it.
- **Needs a change.** The entry says what has to behave differently, not how to build it.
- **Runs on after the close.** It keeps running on the old session or the old voice connection.

Two cases differ, and an entry names the one it means. A **reopen** follows a cut-short recording, for a recorder that connected at startup, so its user ID is known. A **late first open** is a recorder whose startup open failed and that opens later. Nobody knows its user ID until its READY.

- **Needs a change.** `Connect` skips a token that fails to open [`voice/recorders.go:105-110`](https://github.com/7Cav/cavbot2/blob/68c86cad3f93696a28f2d34696ca36611cfa8e8f/voice/recorders.go#L105-L110) and keeps no token once it returns. ## Library facts

### discordgo v0.29.0: `Open` and its retries

- `Open` makes one try and returns its error. A dial that fails, a first frame that isn't Hello, or a close read while it waits for READY each return from `Open` [`wsapi.go:80-86`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L80-L86), [`wsapi.go:104-114`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L104-L114), [`wsapi.go:171-177`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L171-L177). `Open` has no loop.
- The schedule of 1 s doubling to 600 s is `reconnect`, which is unexported [`wsapi.go:878-932`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L878-L932). Its wait starts at 1 s, doubles after each failed `Open` and stops growing at 600 s [`wsapi.go:886`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L886), [`wsapi.go:925-929`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L925-L929). Three callers start it, all on a session that opened: the listener after a read error [`wsapi.go:227-238`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L227-L238), the heartbeat after a failed write or 5 missed answers [`wsapi.go:300-307`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L300-L307), and Op 7 [`wsapi.go:609-613`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L609-L613).
- So a session whose first open fails gets no retry from discordgo. For it, "retries on discordgo's own schedule" can only mean the bot calls `Open` again itself after 1, 2, 4 and so on up to 512 s, then every 600 s.
- `Open` holds the session's write lock throughout [`wsapi.go:57-58`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L57-L58), and discordgo sets no read deadline anywhere in the package. The websocket upgrade has the 45 s handshake timeout of the watch's dialer [`utils/gateway_close.go:27-31`](https://github.com/7Cav/cavbot2/blob/68c86cad3f93696a28f2d34696ca36611cfa8e8f/utils/gateway_close.go#L27-L31). A gateway that accepts the socket and never sends Hello holds `Open`, and the lock, with no end.
- A session that never reached READY identifies on every `Open`, since it has no session ID or sequence to resume with [`wsapi.go:124-135`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L124-L135).
- `Open` counts an Op 9 answer as success. It answers Op 9 with an identify [`wsapi.go:616-629`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L616-L629), logs that the frame wasn't READY, and returns nil [`wsapi.go:179-182`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L179-L182). `utils.OpenSession` catches that case only through `State.User` being nil [`utils/session.go:25-35`](https://github.com/7Cav/cavbot2/blob/68c86cad3f93696a28f2d34696ca36611cfa8e8f/utils/session.go#L25-L35).
- Every identify counts toward Discord's 1000 a day, and at that limit Discord resets the bot token [Discord `gateway.mdx:190`](https://github.com/discord/discord-api-docs/blob/6128d99116af8357db1e4966ebd7f099817a0e04/developers/events/gateway.mdx#L190). Each recorder is an application of its own [`README.md:98`](https://github.com/7Cav/cavbot2/blob/68c86cad3f93696a28f2d34696ca36611cfa8e8f/README.md#L98). A loop at those delays makes about 150 tries in its first day.

### discordgo v0.29.0: close and reopen

- `Close` is `CloseWithCode(1000)` [`wsapi.go:934-938`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L934-L938). It sets `DataReady` false and closes `listening`, which stops the listener and the heartbeat. It sends the close frame, sleeps 1 s holding the session's write lock, closes the socket and emits Disconnect [`wsapi.go:943-989`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L943-L989). Discord's docs say a close with 1000 or 1001 invalidates the session, and the bot shows offline [Discord `gateway.mdx:240-244`](https://github.com/discord/discord-api-docs/blob/6128d99116af8357db1e4966ebd7f099817a0e04/developers/events/gateway.mdx#L240-L244).
- `Close` doesn't stop a `reconnect` loop already running. With the socket already gone, it sends nothing and only emits Disconnect, and the loop's next `Open` connects again [`wsapi.go:888-930`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L888-L930). That session never sent its 1000, so its resume can still succeed.
- `Close` can start a `reconnect`. A heartbeat that left its wait just before the close writes on the closed socket [`wsapi.go:290-299`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L290-L299) and gets gorilla's `ErrCloseSent` or a closed-socket error [gorilla `conn.go:399-401`](https://github.com/gorilla/websocket/blob/v1.5.3/conn.go#L399-L401). It then calls `Close` and `reconnect` [`wsapi.go:300-307`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L300-L307), which logs in again unless `ShouldReconnectOnError` is off. If that heartbeat's write lands before the close frame instead, it can set `DataReady` back to true after `Close` [`wsapi.go:310-312`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L310-L312). The recorder's voice state update guards its write with `DataReady`, so an update through that closed session would then write to no socket, the panic its comment describes [`voice/gateway.go:1283-1309`](https://github.com/7Cav/cavbot2/blob/68c86cad3f93696a28f2d34696ca36611cfa8e8f/voice/gateway.go#L1283-L1309). This is read from the code, and no log has shown it.
- `Close` leaves the handlers alone. Each stays registered until its remove function runs [discordgo `event.go:118-163`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/event.go#L118-L163).
- The same session opens again after `Close`, since that is what `reconnect` does [`wsapi.go:891`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L891). After a READY, though, it only ever resumes. Nothing clears the session ID that READY set [`event.go:242-247`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/event.go#L242-L247) or the sequence [`wsapi.go:653`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/wsapi.go#L653), and the bot can't, since both fields are unexported [`structs.go:126-133`](https://github.com/bwmarrin/discordgo/blob/v0.29.0/structs.go#L126-L133). So an `Open` after a 1000 sends Op 6 for a session Discord has invalidated. Discord answers a resume it can't honor with Op 9 [Discord `gateway-events.mdx:509-517`](https://github.com/discord/discord-api-docs/blob/6128d99116af8357db1e4966ebd7f099817a0e04/developers/events/gateway-events.mdx#L509-L517). discordgo identifies from inside `Open`, and `Open` returns nil before any READY, with the old `State.User` still set, so `utils.OpenSession` can't tell that the new READY never came. The old handlers, state cache and stood-down watch come along. An identify the bot can check needs a new session from `discordgo.New`, which is what `OpenGateway` builds.

## Where the code meets #843's decision

- "The new open retries on discordgo's own schedule" can't come from discordgo for a session that never opened. `Open` makes one try, and the schedule lives in `reconnect`, which only a running session enters. The bot has to run that loop, at the same delays. A loop of its own that reuses one session after a READY would resume every time and never identify, so each try needs a new session or one that never reached READY.
- "Stops only when Discord refuses the token" has nothing in discordgo behind it. discordgo reads no close code, and its loop ignores `ShouldReconnectOnError` once it runs. The refusal reaches the bot as the 4004 that `Open` returns, or as the 4004 the watch's dialer reads after an Op 9.
- "Closes the session with 1000, without waiting on the old voice connection" isn't what `discordgoSession.Close` does today. It waits on every voice connection first, with nothing bounding the wait, and it leaves `ShouldReconnectOnError` on, so the old session can log in again by itself.
- When discordgo has already noticed an outage of the recorder's own gateway as the recording is cut short, its `reconnect` loop is running. `Close` then sends no 1000 and doesn't stop the loop. The old session can resume beside the new one, with the old voice manager listening again. Nothing exported in discordgo ends that loop.
- disgo#588 isn't in the pinned version. #843 says it fixed the lock order in disgo's voice gateway. At `995ee20` that fix isn't there yet, so the old voice gateway's close can still hang against a send.
- "Sentry hears of it once after a minute, as for any gateway outage" doesn't follow from today's watch. A failed first open starts no outage, and `Connect` reports each failure at once.
- Goroutines left running per cut-short recording include more than the voice connection's. Each `OpenGateway` call on a smoke run with `SMOKE_VOICE_DROP_FILE` set also leaves a drop watcher running for good.
- A late first open is a recorder that nothing built at startup knows about. The runtime, temp VC and the smoke tally each took the recorder IDs once, and temp VC's set says it must never change.
